Java4Shell을 보면 “Java를 쓰면 다 위험한가?”라는 질문부터 든다. 실제로는 실행 중인 Java 버전, CPU가 지원하는 기능, 외부 입력이 어떤 처리 경로를 거치는지가 중요했다. 같은 Java 버전이라고 해도 서비스마다 노출 조건이 달라진다. [CERT-EU 권고](https://www.cert.europa.eu/publications/security-advisories/2026-021/pdf) · [Red Hat 권고](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018)

## 1. 보안 문제로 알려지기 전에도 보고가 있었다

Calif가 공개한 기록에 따르면 프로그램이 멈춘다는 제보가 2026년 6월에 나왔다. 9월에는 원인과 수정 제안이 올라왔다. 10월 24일 Calif 연구팀은 AI의 도움을 받아 같은 결함을 별도로 발견하고 Oracle에 보안 문제로 알렸다. 11월 9일에는 기존 제보도 전달하고 공개 일정을 조율해 달라고 요청했다. 이 취약점에는 CVE-2026-114938이라는 번호가 붙었다. [Calif 공개 경위](https://calif.io/java4shell#:~:text=The%20first%20public%20report) · [Oracle 보안 권고](https://www.oracle.com/security-alerts/cspunov2026.html)

- 11월 17일, Oracle과 OpenJDK가 수정판을 공개했다. 미국 CISA는 영향받는 Java 실행 환경을 즉시 업데이트하라고 권고했다. [Oracle 보안 업데이트](https://www.oracle.com/security-alerts/cspunov2026.html) · [CERT-EU 권고](https://www.cert.europa.eu/publications/security-advisories/2026-021/pdf) · [CISA 공지 사본](https://www.aha.org/system/files/media/file/2026/11/cisa-tlp-clear-critical-java-vulnerability-requires-immediate-patching-11-17-2026.pdf)
- 11월 23일, Red Hat이 영향받는 제품과 패치 여부, 바로 업데이트하기 어려울 때의 대처 방법을 담은 권고를 갱신했다. [Red Hat 권고](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018)

## 2. Base64를 읽는 과정에서 왜 문제가 났나

Base64는 이미지처럼 문자로 바로 표시하기 어려운 데이터를 텍스트로 바꾸는 방식이다. JVM은 Java 프로그램을 실행한다. JVM의 한 구현인 OpenJDK HotSpot은 일부 x86-64 CPU에서 여러 바이트를 한꺼번에 처리하는 명령을 써서 Base64를 빠르게 읽는다. 이 최적화 코드가 메모리 범위를 잘못 다루면서 JVM 내부 메모리가 손상될 수 있었다. [Red Hat 기술 설명](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018) · [CERT-EU 기술 설명](https://www.cert.europa.eu/publications/security-advisories/2026-021/pdf)

실제 노출 여부는 세 가지를 같이 봐야 했다. 문제가 있는 JVM 버전인지, CPU와 설정이 해당 최적화 경로를 쓰는지, 외부 입력이 그 디코더까지 들어가는지다. Red Hat에 따르면 AVX-512 VBMI 기능이 없는 x86-64 환경과 ARM64는 이 결함의 영향 범위 밖이다. 서버를 교체하거나 늘릴 때 CPU와 배포 이미지가 바뀔 수 있으니 현재 서버와 대기 중인 서버를 함께 보는 게 좋다. [Red Hat 권고](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018) · [CERT-EU 권고](https://www.cert.europa.eu/publications/security-advisories/2026-021/pdf)

Oracle은 CVSS 3.1 기준으로 8.1점을 매겼고, Red Hat은 자사 제품에서 이 문제를 Critical로 분류했다. 어느 서버부터 볼지는 점수와 함께 실제 요청이 어디까지 들어가는지를 봐야 한다. Red Hat에 따르면 Keycloak은 로그인 전 요청에서도 Base64를 처리할 수 있다. 인터넷에 공개된 Keycloak이 영향받는 JVM을 쓰고 있다면 먼저 확인할 이유가 있다. [Oracle CVE 정보](https://linux.oracle.com/cve/CVE-2026-114938.html) · [Red Hat의 제품별 안내](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018)

### 내 서비스가 영향을 받는지 확인하는 순서

먼저 외부 요청을 받는 서비스가 Base64를 어디에서 읽는지 확인한다. 다음으로 실제 JVM 빌드와 CPU 기능, 실행 설정을 살핀다. 취약한 상태라면 서비스 계정이 닿는 데이터와 내부 서비스도 확인한다. 앱의 라이브러리를 바꿔 입력 경로 하나를 닫아도, 같은 JVM을 쓰는 다른 앱과 경로는 따로 확인해야 한다. [CERT-EU 권고](https://www.cert.europa.eu/publications/security-advisories/2026-021/pdf) · [Red Hat 제품별 영향](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018)

| 조사 대상 | 왜 필요한가 | 예시 증빙 |
| --- | --- | --- |
| 공급사와 빌드 | 제품명이나 메이저 버전이 같아도 수정 여부가 다를 수 있다. | 패키지 권고, 컨테이너 이미지 다이제스트, 실행 프로세스의 런타임 빌드 |
| CPU와 배치 노드 | 특정 하드웨어 최적화가 활성화되는지 판단한다. | 노드별 아키텍처·CPU 기능, VM에 노출된 기능, 대기 노드와 오토스케일 템플릿 |
| 신뢰 경계와 인증 순서 | 미인증, 인증 후, 내부 전달 등 입력의 도달 경로에 따라 우선순위가 바뀐다. | 애플리케이션 소유자의 데이터 흐름, 인증 구성, 라우팅·서비스 인벤토리 |
| 런타임 권한과 데이터 | 원격 코드 실행이 가능한 경우 그 프로세스가 접근할 수 있는 범위를 잡는다. | 서비스 계정 권한, 파일·시크릿 접근, 외부 연결 정책 |
| 업무 의존성과 재시작 방식 | 패치 적용에 필요한 롤링 배포나 정지 창을 판단한다. | 복제본 수, 가용 영역, 인증·메시지 처리 상태 확인, 롤백 가능한 이미지 목록 |

## 3. 공격이 시도됐다는 기록은 있었나

GreyNoise는 스캔과 악용 시도를 봤다고 밝혔다. 조사할 때 확인한 대시보드에는 해당 센서에서 성공한 공격이 확인되지 않았다고 적혀 있었다. 프로그램이 멈추거나 메모리가 노출되거나 원격에서 코드가 실행되는 건 조건에 따라 가능한 결과다. 어느 조직이 피해를 입었는지, 어떤 데이터가 유출됐는지, 공격이 몇 번 성공했는지는 이 관측으로 알 수 없다. [GreyNoise 관측 대시보드](https://java4shell.events.greynoise.io/) · [Sophos 권고](https://www.sophos.com/en-us/security-advisories/sophos-sa-20261118-java4shell)

### 의심스러운 요청이 보이면 다음에 볼 것

탐지 기록에 요청이 찍혔다면 실제로 JVM의 해당 코드까지 들어갔는지, 이후 프로세스에 변화가 있었는지, 데이터가 나갔는지 따로 봐야 한다. 로그의 시간대와 같은 요청을 식별하는 ID를 맞춰서 JVM 오류, 재시작, 새 프로세스 실행, 네트워크 연결, 자격증명 사용 기록을 대조할 수 있다. 평소 얼마나 자주 나던 오류인지도 비교한다. 예를 들어 오래전부터 반복된 메모리 부족은 다른 문제였을 수 있다. [GreyNoise 관측 대시보드](https://java4shell.events.greynoise.io/) · [Sophos 확인 범위](https://www.sophos.com/en-us/security-advisories/sophos-sa-20261118-java4shell)

바로 업데이트하기 어렵다면 CERT-EU와 Red Hat이 안내한 대로 Base64 최적화를 잠시 끄고 JVM을 다시 시작할 수 있다. 적용한 뒤에는 서비스가 실제로 어떤 JVM 빌드와 설정으로 돌아가는지 확인한다. 서버의 Java 패키지를 바꿔도 컨테이너나 제품에 들어 있는 Java는 그대로일 수 있다. 이런 경우 해당 이미지나 제품의 업데이트 절차를 따른다. [CERT-EU 대응 절차](https://www.cert.europa.eu/publications/security-advisories/2026-021/pdf) · [Red Hat 제품별 대응](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018)

### 업체마다 안내가 다른 이유

Oracle은 수정판을 내놨고, Adoptium은 Temurin 17의 수정 빌드로 17.0.21.1+2를 안내했다. AWS는 Amazon Linux별 Corretto 패키지와 서비스별 완화 상태를 나눠서 알렸고, 웹 방화벽(WAF) 규칙도 제공했다. AWS가 관리형 서비스에서 한 조치, 고객이 직접 Corretto 이미지를 바꾸는 작업, 고객 쪽 웹 방화벽 설정은 각각 확인해야 한다. Red Hat도 제품에 Java가 포함돼 있으면 그 제품에서 지원하는 방법으로 업데이트하라고 안내했다. [Oracle 릴리스 목록](https://docs.oracle.com/en-us/iaas/releasenotes/java-management/jdk-cspu-november-2026.htm) · [Adoptium Temurin 가이드](https://adoptium.net/news/2026/11/temurin-november-2026-cspu-java4shell/) · [AWS 보안 공지](https://aws.amazon.com/security/security-bulletins/2026-189-aws/) · [Red Hat 권고](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018)

| --- | --- | --- |

| 공급사가 제시한 최적화 비활성화 | 취약 코드 경로 사용을 임시로 막는다. | 실행 중인 JVM에 설정이 적용됐는지, 레이턴시와 CPU 사용률, 롤링 배포 누락 |
| WAF·접근 경로 제한 | 적용 범위의 외부 요청을 제한하거나 관측한다. | 실제 활성화와 정책 동작, 정상 요청 영향, 프록시를 지나지 않는 경로와 내부 전달 경로 |
| 서비스 권한 축소 | 프로세스가 손상됐을 때 데이터와 자격증명의 접근 범위를 줄인다. | 워크로드 신원 권한, 시크릿 마운트, 네트워크 허용 범위 |

## 5. 크래시 보고와 패치 과정에서 아쉬웠던 점

최초 크래시 제보와 보안 패치 공개 사이에 몇 달이 있었다. 외부 입력을 처리하다 공통 실행 환경의 메모리가 손상된다면, 일반 오류 제보에서도 보안 문제를 검토할 필요가 있다. 내부에서 해당 제보를 어떻게 분류했는지는 공개 자료에 나오지 않는다. 패치가 나온 뒤에도 공급사와 제품에 따라 적용 방법이 달라서, 각 서비스에서 실제로 어떤 JVM을 쓰는지 확인해야 한다. [Calif 공개 경위](https://calif.io/java4shell#:~:text=The%20first%20public%20report) · [Red Hat 권고](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018) · [AWS 서비스별 완화 현황](https://aws.amazon.com/security/security-bulletins/2026-189-aws/)

| 우선순위 | 담당과 개선 조치 | 완료를 확인할 기록 |
| --- | --- | --- |
| 1. 인터넷 노출 서비스부터 수정 | 런타임 운영팀이 외부 요청과 인증을 처리하는 서비스의 JVM, CPU, 노드별 빌드를 확인하고 수정판으로 교체한다. | 운영·대기·자동 확장 노드의 빌드, 서비스 재시작과 인증 검증, 미확인 노드 수 |
| 2. 노출 기간의 이상 조사 | 보안팀이 악용 시도와 실제 프로세스·자격증명 이벤트를 대조한다. 패치 배포 이력과 과거 노출에 대한 조사 상태를 각각 관리한다. | 로그 보존 범위, 이벤트 상관 분석, 운영 환경에 수정 JVM이 반영된 시각 |
| 3. 크래시 분류와 테스트 개선 | 개발팀이 외부 입력, 네이티브 메모리 경계, 공통 런타임 영향을 보안 검토 기준에 넣고 일반·고속 디코딩 경로를 CPU 기능별로 비교 시험한다. | 보안 검토 기준, CPU별 CI 결과, 오류 처리 일관성과 메모리 검사 결과 |

## 6. 조사한 뒤 남은 질문

이 사례를 보고 나니 크래시 제보를 읽을 때 외부 입력이 들어올 수 있는지, 실행 프로그램의 메모리까지 손상되는지도 같이 봐야겠다는 생각이 들었다. 실제 피해를 더 확인하려면 각 조직의 사고 보고나 조사 기록이 필요하다. 패치가 얼마나 퍼졌는지를 보려면 배포판과 제품별 공지에 더해, 실제 운영 서버에서 어떤 버전이 실행되는지 집계해야 한다.
