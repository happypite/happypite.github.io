NGINX2Root라는 이름을 보고 NGINX 결함만으로 서버 관리자 권한까지 얻을 수 있는지 궁금했다. 연구진이 확인한 첫 영향은 요청을 처리하는 워커 권한으로 코드가 실행될 수 있다는 점이다. 호스트 관리자 권한까지 얻은 실험에는 별도의 리눅스 커널 결함도 있었다. 실제 영향 범위는 워커의 권한과 서버 설정에 따라 달라진다. [CERT-EU 권고](https://cert.europa.eu/publications/security-advisories/2026-022/) · [Cloudflare Radar 분석](https://radar.cloudflare.com/zero-wire/nginx2root)

## 1. 언제 발견하고 고쳤나

Wiz는 자체 AI 도구의 도움을 받아 취약점을 찾았다고 설명했다. 이 설명은 Wiz의 조사 과정에 관한 것이다. 실제 공격에 AI가 쓰였는지, 다른 취약점도 같은 방법으로 찾았는지는 여기서 알 수 없다. ## 2. NGINX 어디에서 문제가 났나

HTTP/2는 한 연결에서 주고받을 데이터 양을 조절한다. CVE-2026-123007은 이 과정에서 쓰는 숫자가 허용 범위를 벗어났을 때 제대로 처리하지 못한 문제다. 그 결과 워커가 배정받은 메모리 밖에 데이터를 쓸 수 있었다. 워커가 멈추면 접속에 문제가 생길 수 있고, 조건에 따라 워커 권한으로 원격에서 코드가 실행될 수도 있다. 정적 페이지만 제공하는 서버도 인터넷에서 HTTP/2 연결을 직접 받으면 점검 대상이다. [NGINX 공식 권고](https://nginx.org/en/security_advisories.html) · [CERT-EU 기술 설명](https://cert.europa.eu/publications/security-advisories/2026-022/)

| CVE | 결함이 발생한 곳 | 운영 점검 대상 |
| --- | --- | --- |
| CVE-2026-123007 | HTTP/2 흐름 제어의 정수 연산과 힙 경계 | 외부에서 접근 가능한 HTTP/2 리스너 |
| CVE-2026-123633 | HTTP/2에서 해제된 객체 재사용 | HTTP/2를 받는 리버스 프록시 |
| CVE-2026-121810 | HTTP/3에서 해제된 객체 재사용 | HTTP/3을 받는 리버스 프록시 |
| CVE-2026-123634 | DNS 응답 처리 중 해제된 객체 재사용 | NGINX DNS resolver를 쓰는 구성 |
| CVE-2026-113425 | 메일 프록시에서 해제된 객체 재사용 | NGINX 메일 프록시 모듈을 쓰는 구성 |

표에서 반복되는 ‘메모리 해제 후 사용(use-after-free)’은 이미 돌려준 메모리를 다른 코드가 계속 쓰려고 하는 문제다. 다섯 건 모두 메모리를 잘못 다룬 결함이지만 발생한 위치와 조건은 서로 다르다. 이 표로 어떤 기능부터 볼지 좁히고, 실제 영향은 사용 중인 버전과 설정을 업체 공지에 대조해 확인한다. [NGINX 공식 권고](https://nginx.org/en/security_advisories.html) · [CERT-EU 기술 설명](https://cert.europa.eu/publications/security-advisories/2026-022/)

워커가 읽을 수 있는 파일, 컨테이너가 연결할 수 있는 내부 서비스, 호스트에서 할 수 있는 일은 환경마다 다르다. 별도로 보고된 리눅스 커널 결함은 SCTP라는 전송 프로토콜을 처리하는 부분에서 발견됐다. NGINX를 업데이트한 뒤에도 커널 쪽은 사용 중인 배포판의 안내를 확인해야 한다. [Cloudflare Radar 설명](https://radar.cloudflare.com/zero-wire/nginx2root) · [MyCERT 권고](https://mycert.org.my/portal/advisory?id=MA-1512.112026)

### 같은 NGINX여도 설치 구조에 따라 달라진다

| 실제 배치 | 먼저 확인할 질문 | 확인에 필요한 자료 |
| --- | --- | --- |
| 인터넷 → NGINX → 애플리케이션 | NGINX가 직접 어떤 프로토콜을 종단하는가. | 로드밸런서 리스너, NGINX 유효 설정, 실행 중인 패키지 빌드 |
| 인터넷 → CDN → NGINX 원본 | 원본에 직접 닿는 다른 경로가 있는가. CDN과 원본 사이의 연결은 어떤 설정인가. | DNS·인증서·로드밸런서 자산 목록, 보안 그룹, 원본 접속 로그 |
| 컨테이너·Kubernetes Ingress | 어떤 이미지가 실제 실행 중이며 워커가 어느 시크릿과 내부 서비스에 접근할 수 있는가. | 실행 이미지 다이제스트, 서비스 계정 권한, 네트워크 정책, 노드 커널 버전 |
| 제품에 포함된 NGINX 또는 배포판 패키지 | 업스트림 버전 표가 이 설치본에 그대로 적용되는가. | 제품 공급사 권고, 배포판 수정 패키지 번호, 장비·이미지 배포 기록 |
| HTTP/3·DNS·메일 프록시 | HTTP/2를 끈 뒤에도 조사 대상 모듈이 남아 있는가. | 활성 모듈과 설정, 운영 용도, 해당 CVE별 공급사 권고 |

버전 번호만 보면 헷갈릴 수 있다. Ubuntu는 1.30.7보다 낮은 버전 번호에도 수정 코드를 넣어 배포했다. 서버가 표시하는 숫자 앞부분만 보고 취약하다고 판단하면, 이미 고쳐진 패키지까지 점검 대상에 넣게 된다. CDN을 사용하는 환경에서는 원본 서버나 테스트용 연결 지점에 외부에서 바로 접속할 수 있는지도 봐야 한다. [Ubuntu CVE별 패치 상태](https://ubuntu.com/security/CVE-2026-123007) · [Cloudflare 원본 보호 설명](https://blog.cloudflare.com/nginx2root/) · [CERT-EU 권고](https://cert.europa.eu/publications/security-advisories/2026-022/)

## 3. 실제 피해는 어디까지 확인됐나

공개 자료를 비교해 보니 기관마다 확인한 범위가 달랐다. 연구진은 CVE-2026-123007로 원격 코드 실행이 가능하다는 걸 검증했다. CERT-EU는 공개일인 11월 18일 기준으로 실제 악용 보고를 확인하지 못했다. 서호주 보안관제센터(WASOC)는 이후 다섯 건 중 하나 이상에 대한 악용 보고를 인지했다고 밝혔다. 공지에는 해당 CVE와 피해 조직이 나오지 않으며, 서호주 정부망에서는 보고를 받지 않았다고 했다. 말레이시아 MyCERT도 11월 21일까지 검토한 자료에서 실제 악용 보고를 확인하지 못했다. 공개 자료로는 특정 조직이 어떤 피해를 입었는지 알기 어렵다. [CERT-EU 권고](https://cert.europa.eu/publications/security-advisories/2026-022/) · [WASOC 권고](https://soc.cyber.wa.gov.au//advisories/20261119001-NGINX2Root/) · [MyCERT 권고](https://mycert.org.my/portal/advisory?id=MA-1512.112026)

### 인터넷에 노출된 수치는 어떻게 읽나

Censys는 인터넷에 응답한 서비스에서 HTTP/2가 보이는지, 서버가 버전을 어떻게 표시하는지 보고 집계한다. 버전을 숨긴 서비스는 포함 여부를 선택할 수 있다. 일정 기간 HTTP/2가 보이지 않으면 완화된 것으로 분류하는 기준도 있다. 한 조직이 서비스 여러 개를 운영할 수 있고, Ubuntu 예시처럼 표시된 버전만으로 수정 코드가 들어갔는지 모르는 경우도 있다. 이 숫자를 인용하려면 언제 집계했는지, 무엇을 한 건으로 셌는지, 버전 미상을 포함했는지, 어느 CVE인지를 함께 적어야 한다. 피해 조직 수와 공격 성공률은 이 집계로 알 수 없다. [Censys 노출 추적기](https://nginx2root.censys.com/) · [Censys 조사 방법](https://censys.com/advisory/nginx2root/)

### 워커가 멈췄다면 어떤 기록을 볼까

1. 먼저 시각을 맞춘다. 워커가 멈춘 때에 호스트나 컨테이너가 재시작됐는지, 설정이나 CPU·메모리 사용량에 변화가 있었는지 본다. 정상 배포, 메모리 부족, 다른 장애도 비슷한 증상을 만들 수 있다.
2. 같은 서버에서 무슨 일이 있었는지 본다. 새 프로세스 실행, 예상 밖의 외부 연결이나 파일 변경, 서비스 계정 활동 증가가 같은 시각에 있었는지 대조한다. 로그가 비어 있는 구간도 적어 둔다.
3. 워커 권한을 확인한다. TLS 키 같은 자료, 접속 자격증명, 공유 저장소, 내부 서비스와 노드 가운데 그 워커가 실제로 접근할 수 있던 곳부터 본다. 워커가 멈췄다는 기록만으로 호스트 관리자 권한을 얻었거나 데이터가 유출됐는지는 판단할 수 없다.
4. 판단한 근거를 남긴다. 당시 이미지와 패키지, 배포 이력, 관련 로그를 보관한다. 고객이 겪은 영향과 침해 가능성, 자료가 없어 알 수 없는 부분을 각각 적는다. 시각이나 관련 로그가 없다면 어떤 기간과 범위의 기록을 갖고 있는지부터 밝힌다. [CERT-EU 침해 평가 권고](https://cert.europa.eu/publications/security-advisories/2026-022/)

## 4. 나온 패치와 임시 대책

F5는 11월 18일 NGINX 오픈소스 안정판 1.30.7과 메인라인 1.31.9에서 다섯 건을 수정했다. 운영에서는 그 수정이 포함된 지원 버전을 고르면 된다. NGINX Plus, 리눅스 패키지, Kubernetes Ingress, 다른 제품에 포함된 NGINX는 각 공급사가 안내한 버전이나 백포트(기존 버전에 옮긴 수정 코드)를 확인한다. CERT-EU는 인터넷에 공개된 서버를 먼저 업데이트하라고 권고했다. 바로 어렵다면 노출된 HTTP/2를 끌 수 있는데, 이 조치가 적용되는 건 HTTP/2 관련 두 건이다. Cloudflare는 자사 HTTP 프록시가 클라이언트 연결을 먼저 받는 구성에서 HTTP/2·HTTP/3 관련 위험이 줄어든다고 설명했다. NGINX 원본 서버에 바로 연결되는 경로가 있다면 그 연결에는 이 보호가 적용되지 않는다. [F5 보안 공지](https://my.f5.com/manage/s/article/K000164058) · [CERT-EU 권고](https://cert.europa.eu/publications/security-advisories/2026-022/) · [Cloudflare 설명](https://blog.cloudflare.com/nginx2root/)

### 대책별로 어디까지 막을 수 있나

| 대응 수단 | 얻는 효과 | 남는 위험과 완료 증거 |
| --- | --- | --- |

| 최소 권한과 비밀·네트워크 분리 | 워커가 손상됐을 때 접근 가능한 자산을 줄인다. | 런타임 결함 자체는 그대로이며, 배포 전후 권한·연결 허용 범위를 비교해야 한다. |

## 5. 어디가 미흡했고 무엇부터 고칠까

개발 쪽 문제는 숫자의 허용 범위와, 이미 해제한 메모리를 언제까지 참조할 수 있는지에서 생겼다. 대응에서도 HTTP/2를 끄는 방법은 두 건에만 통하고, 원본 NGINX와 각 배포판·제품의 패치 방법이 달랐다. F5 내부에서 어떤 테스트가 빠졌는지나 각 조직이 언제 패치를 끝냈는지는 자료에 없다. 표는 공개 자료에서 본 문제를 바탕으로, 개발팀과 운영팀이 무엇부터 확인하면 좋을지 적은 것이다. [NGINX 공식 권고](https://nginx.org/en/security_advisories.html) · [CERT-EU 권고](https://cert.europa.eu/publications/security-advisories/2026-022/)

## 6. 조사한 뒤 남은 질문

운영하는 입장이라면 인터넷 요청이 어디로 들어오는지, 실제로 어떤 버전이 돌고 있는지, 그 워커가 무엇까지 읽을 수 있는지부터 볼 것 같다. 실제 침해 사례라고 쓰려면 어느 취약점이 언제 악용됐고 어떤 피해가 났는지 확인해 줄 기관이나 피해 조직의 자료가 필요하다. F5가 내부에서 어떻게 검토했는지, 개별 조직에서 배포가 얼마나 지연됐는지도 공개 자료로는 알기 어렵다. [WASOC 권고](https://soc.cyber.wa.gov.au//advisories/20261119001-NGINX2Root/) · [F5 공지](https://my.f5.com/manage/s/article/K000164058)
